# 软件开发代码质量与测试规范

## 1. 总体要求

每次完成新功能、修改已有功能或重构代码后，必须执行代码质量检查与测试，确保功能正确性、可维护性、安全性和可靠性。

遵循以下原则：

1. **正确性优先**：重构不得意外改变原有功能行为；功能修改必须满足明确的验收标准。
2. **风险驱动**：根据代码变更的复杂度、影响范围和潜在风险确定测试深度。
3. **自动化优先**：代码分析、常规测试和质量度量应尽可能自动完成。
4. **人工审核**：重构方案、系统级测试及质量例外必须经人工审核。
5. **质量不退化**：不得因本次修改引入新的严重质量问题或降低已有测试质量。
6. **结果可验证**：所有质量结论必须有实际检查结果支持，不得将未执行、执行失败或结果不可用的检查标记为通过。

## 2. 标准执行流程

每次功能完成后，按以下顺序执行：

### 阶段一：变更分析与测试基线

1. 分析变更目标、修改范围、受影响模块及外部依赖。
2. 明确预期行为、验收标准及潜在风险。
3. 将变更划分为低、中、高三级风险。
4. 执行现有相关测试，记录测试结果、已知问题及可获得的覆盖率数据。
5. 若现有测试不足以保护原有行为，先补充必要的行为测试。

### 阶段二：代码质量检查

1. 检查全部24种典型代码异味。
2. 执行静态分析、复杂度、依赖、资源管理、并发及安全检查。
3. 根据检查结果生成分级报告与重构方案。
4. 提交人工审核。

**未经批准，不得执行由代码异味检查提出的重构。**

### 阶段三：重构

1. 按照人工审核通过的方案实施重构。
2. 采用小步修改，每次实质性修改后运行相关测试。
3. 验证原有外部行为及接口契约没有发生非预期变化。
4. 重新检查受影响代码的质量。

发现需要超出审核范围的修改时，必须重新提交审核。

### 阶段四：测试设计与执行

1. 根据变更风险补充或修改函数级、模块级及必要的集成测试。
2. 采用适当的黑盒和白盒测试设计方法。
3. 执行测试并分析失败原因。
4. 使用覆盖率和变异测试工具衡量测试充分性。
5. 执行相关回归测试。
6. 必要时设计系统级测试方案并提交人工审核。

### 阶段五：质量验收

1. 汇总代码质量、测试、覆盖率及变异测试结果。
2. 判断是否满足质量门禁。
3. 对未解决问题和质量例外提交人工审核。
4. 生成最终质量报告。

任何必要检查失败、缺失或审核未完成时，不得宣称通过最终验收。

## 3. 代码质量检查

### 3.1 代码异味检查

必须检查以下24种典型代码异味：

1. 神秘命名
2. 重复代码
3. 过长函数
4. 过长参数列表
5. 全局数据
6. 可变数据
7. 发散式变化
8. 霰弹式修改
9. 依恋情结
10. 数据泥团
11. 基本类型偏执
12. 重复的 switch
13. 循环语句
14. 冗赘元素
15. 夸夸其谈通用性
16. 临时字段
17. 过长消息链
18. 中间人
19. 内幕交易
20. 过大类
21. 异曲同工的类
22. 纯数据类
23. 被拒绝的遗赠
24. 注释

检查范围包括所有新增、修改代码及受影响的相关代码。

#### 异味程度

所有检查项按以下三级分类：

| 等级     | 判定标准                  |
| ------ | --------------------- |
| 异味存在   | 存在明确的设计或维护性问题，有充分证据支持 |
| 异味存在倾向 | 存在潜在问题，但尚不足以确定必须重构    |
| 不存在异味  | 未发现有实际意义的相关异味         |

不得仅根据循环、注释、数据类等语法结构的存在直接认定为代码异味。

#### 检查结果

按照异味程度分组列出全部24项检查结果。

对于“异味存在”和“异味存在倾向”，必须提供：

- 异味名称、位置和程度。
- 判断依据及潜在影响。
- 建议重构方案。
- 重构风险及可能造成的行为变化。

“不存在异味”的项目可以集中列出。

重构方案由人工决定批准、修改、暂缓或拒绝，未批准的方案不得执行。

### 3.2 静态分析与专项检查

除代码异味外，还必须检查：

| 检查类别  | 主要内容                              |
| ----- | --------------------------------- |
| 静态分析  | 空引用、未初始化数据、未使用代码、不可达代码、异常处理及编译器警告 |
| 复杂度   | 圈复杂度、认知复杂度、嵌套深度、函数及类的规模           |
| 架构与依赖 | 循环依赖、模块耦合、职责边界及分层规则               |
| 资源管理  | 内存、文件句柄、Socket、子进程、异步任务及资源释放      |
| 并发安全  | 竞态、死锁、共享可变状态、重入、取消操作及状态一致性        |
| 安全    | 命令注入、路径遍历、敏感信息泄露、权限边界及依赖漏洞        |

新增严重静态分析问题及高危安全问题必须修复，无法修复的非安全质量问题应提交人工审核。

复杂度阈值应结合项目特点确定，不得单纯为了降低指标而进行无意义拆分。

## 4. 测试规范

### 4.1 测试层次

**函数级测试**

验证函数或最小逻辑单元的输入、输出、边界及异常行为。

**模块级测试**

验证模块内部协作、公开接口、状态管理及模块契约。

**集成测试**

验证实际组件间的交互，例如配置文件处理、进程控制及外部服务调用。

**系统级测试**

验证完整系统在实际或隔离环境中的运行行为，执行前必须人工审核。

常规函数级、模块级及已授权的集成测试应尽可能自动执行。

### 4.2 测试设计方法

测试必须同时考虑黑盒和白盒测试。

#### 黑盒测试

根据实际功能采用：

- 等价类划分。
- 边界值分析。
- 决策表测试。
- 状态迁移测试。
- 异常路径测试。
- 错误推测。
- 输入组合测试。

至少覆盖适用的正常输入、无效输入、边界条件和异常行为。

黑盒测试优先采用基于明确规格的机械化生成。对于能够形式化描述的输入范围、等价类、决策表、状态迁移和参数组合，自动生成测试样例；对于需要领域经验的异常场景、错误推测及规格不明确的行为，由模型提出测试建议并给出依据。无法确定预期结果时，不得自行将当前实现作为正确性标准，应提交人工审核。

#### 白盒测试

使用明确的结构覆盖准则：

| 覆盖准则             | 使用场景                   |
| ---------------- | ---------------------- |
| DC（判定覆盖）         | 基础判定验证                 |
| CDC（条件/判定覆盖）     | 普通模块                   |
| CC/DC（条件组合/判定覆盖） | 组合条件较复杂的普通模块           |
| MC/DC（修正条件/判定覆盖） | sing-box 核心控制模块的关键复合判定 |

普通模块主要采用 CDC 或 CC/DC，复杂核心判定优先采用 MC/DC。

应结合实际逻辑和可达输入选择覆盖准则，不要求对所有简单判定机械实施 MC/DC。

结构覆盖不能代替功能正确性测试。

### 4.3 契约、状态与异常测试

当模块涉及外部依赖或状态管理时，必须根据适用性验证：

- 输入输出格式与接口约定。
- 错误处理及异常传播。
- 正常与非法状态转换。
- 重复操作和幂等性。
- 超时、取消及中断。
- 故障恢复。
- 并发状态一致性。
- 资源释放。
- 接口及配置格式兼容性。

对于输入空间较大的模块，可以增加属性测试或模糊测试。发现的有效问题应尽可能转化为可重复执行的回归样例。

### 4.4 sing-box 核心控制模块

sing-box 核心控制逻辑属于高风险模块，重点检查以下行为：

| 测试领域 | 检查内容                     |
| ---- | ------------------------ |
| 配置管理 | 配置生成、校验、更新、序列化、版本兼容及失败处理 |
| 进程管理 | 启动、停止、重复操作、异常退出、超时及重试    |
| 状态管理 | 状态一致性、非法转换、并发控制及异常恢复     |
| 外部调用 | 命令参数、退出码、输出处理、权限不足及取消    |
| 资源管理 | 文件、进程、连接、任务及其他资源释放       |
| 安全   | 输入校验、命令注入、敏感信息及权限边界      |

核心复杂判定优先采用 MC/DC。

函数级测试可以使用模拟依赖；集成测试应根据需要使用真实 sing-box 可执行程序。

涉及路由、DNS、网络接口、防火墙等宿主机状态的操作，必须纳入系统级测试审核范围。

## 5. 测试质量度量

### 5.1 覆盖率

默认要求：

**分支覆盖率 ≥90%。**

.NET 项目使用 Coverlet，其他语言使用适配工具。

报告至少包含：

- 分支覆盖率。
- 行覆盖率。
- 方法覆盖率（适用时）。
- 项目、相关模块及变更代码的覆盖情况。
- 未覆盖分支及其原因。

分支覆盖率为主要量化指标，行覆盖率和方法覆盖率作为辅助参考。

允许按预先明确的规则排除自动生成代码和第三方库，不得临时扩大排除范围以满足阈值。

Coverlet 测量的分支覆盖率不等同于 MC/DC 覆盖率。后者必须通过专用工具或测试矩阵独立验证。

### 5.2 变异测试

默认要求：

**变异得分 ≥80%。**

.NET 项目使用 Stryker.NET，其他语言使用相应工具。

报告至少包含：

- 变异得分及统计口径。
- 被杀死、存活、未覆盖、超时及其他类别的变异体数量。
- 有效存活变异体及其原因。
- 补充测试与重新执行结果。

对于存活变异体，应分析测试为何未能发现代码行为变化，并补充有意义的测试。

不得通过削弱测试、无意义断言或不合理排除变异体提高分数。

### 5.3 回归测试

任何功能修改或重构均须执行受影响范围内的回归测试。

修复缺陷时，应尽可能增加能够复现该缺陷的测试。

公共接口、共享组件及跨模块依赖发生变化时，必须扩大回归范围。

### 5.4 性能与稳定性测试

性能敏感、资源密集或长期运行的模块，根据风险执行：

- 延迟与吞吐量测试。
- CPU 和内存使用率测试。
- 并发压力测试。
- 长时间稳定性测试。
- 资源泄漏检查。

性能结论应基于可比较的测试环境和多次测量，不得仅依赖单次运行结果。

## 6. 风险分级与执行策略

### 6.1 风险分级

| 等级  | 典型修改                                 |
| --- | ------------------------------------ |
| 低风险 | 文案、简单 UI、无行为影响的局部调整                  |
| 中风险 | 普通功能、模块内部逻辑、一般接口实现                   |
| 高风险 | sing-box 控制、进程、网络、并发、安全、公共接口及跨模块架构变更 |

无法确定风险时，按较高等级处理。

### 6.2 测试要求

| 检查项目       | 低风险  | 中风险  | 高风险       |
| ---------- | ---- | ---- | --------- |
| 代码异味检查     | 相关代码 | 相关代码 | 相关及影响模块   |
| 静态分析       | 必须   | 必须   | 必须        |
| 函数/模块测试    | 适用时  | 必须   | 必须        |
| 分支覆盖率 ≥90% | 适用时  | 必须   | 必须        |
| 变异得分 ≥80%  | 适用时  | 必须   | 必须        |
| MC/DC      | 按需   | 按需   | 核心复合判定    |
| 状态与异常测试    | 按需   | 适用时  | 必须考虑      |
| 集成测试       | 按需   | 适用时  | 涉及组件交互时必须 |
| 回归测试       | 相关范围 | 相关模块 | 扩大相关范围    |
| 系统级测试      | 人工审核 | 人工审核 | 人工审核      |

对于没有可执行分支的修改，不机械要求独立计算覆盖率或变异得分。

### 6.3 执行频率

| 时机       | 任务                   |
| -------- | -------------------- |
| 每次实质性修改后 | 编译、静态检查、相关测试         |
| 功能完成后    | 代码异味、完整相关测试、覆盖率、变异测试 |
| 重构完成后    | 行为回归及质量复查            |
| 合并或发布前   | 全量相关回归与必要的集成测试       |
| 定期质量检查   | 更大范围的变异、性能与稳定性测试     |

## 7. 系统级测试与人工审核

所有系统级测试必须事先提交审核方案，至少说明：

1. 测试目标与范围。
2. 测试环境与步骤。
3. 预期结果。
4. 外部资源及潜在风险。
5. 失败处理、环境恢复与回滚措施。

未经批准，不得执行系统级测试。

优先在容器、虚拟机或其他隔离环境中执行。

测试完成后，记录实际结果、发现的问题及环境恢复情况。

## 8. 自动化与可重复性

所有适合自动化的测试应尽可能通过脚本或持续集成流程执行。

测试必须尽量满足：

- 可以在干净环境中重复执行。
- 测试之间相互独立。
- 测试依赖和工具版本明确。
- 随机测试记录可复现的种子。
- 不依赖未声明的外部状态。
- 不意外修改真实用户数据。
- 测试完成后清理临时资源。
- 不稳定测试必须调查原因，不得通过无限重试或直接禁用掩盖失败。

测试工具必须与项目技术栈兼容；工具不支持的指标应选择替代工具或提供其他验证方法。

无法完成必要检查时，应记录原因，并将对应结果标记为未验证。

## 9. 质量门禁与例外处理

### 9.1 默认质量标准

| 指标      | 验收标准             |
| ------- | ---------------- |
| 编译      | 成功               |
| 24种代码异味 | 全部检查并报告          |
| 静态分析    | 无新增未经批准的严重问题     |
| 重构      | 按人工审核方案执行        |
| 必需测试    | 全部通过             |
| 分支覆盖率   | ≥90%             |
| 变异得分    | ≥80%             |
| 核心复杂判定  | 满足选定的 MC/DC 验证要求 |
| 回归测试    | 相关测试通过           |
| 安全      | 无新增高危问题          |
| 系统级测试   | 执行前人工审核          |

以上要求按风险等级和适用范围执行。

### 9.2 质量例外

当已有代码无法满足阈值时，应记录历史基线，确保本次修改不进一步降低质量，并提出改善方案。

无法满足适用质量门禁时，必须提交人工审核。

禁止通过以下方式规避质量检查：

- 降低覆盖率或变异得分阈值。
- 删除失败测试。
- 弱化有效断言。
- 无依据地排除代码或变异体。
- 隐瞒编译、分析或测试失败。
- 将未执行的测试标记为通过。

经批准的例外必须记录原因、风险和后续处理方案。

## 10. 质量报告与最终验收

每次功能完成后，生成统一质量报告，至少包含：

### 10.1 变更信息

- 变更目标、范围与风险等级。
- 涉及模块及主要修改内容。

### 10.2 代码质量

- 24种代码异味分级结果。
- 静态分析及专项检查结果。
- 重构方案、人工审核决定和执行情况。

### 10.3 测试结果

- 测试环境及工具版本。
- 测试类型、数量、通过与失败情况。
- CDC、CC/DC、MC/DC 等适用结构覆盖准则的验证结果。
- 分支覆盖率及未覆盖分支。
- 变异得分及存活变异体分析。
- 回归测试结果。
- 未执行测试及原因。

### 10.4 未解决问题

- 剩余缺陷与质量风险。
- 不达标指标。
- 质量例外及人工审核结果。
- 后续建议。

### 10.5 最终结论

| 结论      | 判定条件                  |
| ------- | --------------------- |
| 通过      | 全部适用质量门禁满足，必要审核已完成    |
| 有条件通过   | 存在人工明确批准且已记录的非阻断性质量例外 |
| 不通过     | 存在未解决的阻断性质量问题或测试失败    |
| 待审核/未验证 | 必要审核未完成，或关键检查缺少可信结果   |

仅当符合相应条件时，才能给出对应结论。

**覆盖率和变异得分是测试充分性的最低量化要求，不构成软件正确性的证明。最终验收必须同时依据功能测试、结构覆盖、异常行为、回归测试及实际质量风险进行判断。**
